## 0. 结论

**发布判定：BLOCK。**

当前候选在新的冻结口径下仍有 5 项 P0：同性/异性关系双层模型没有可计算输入与第二层结果；证据不足的硬条件仍会用假设比例直接缩小主人数且没有“未计入”状态；缺少可靠人口锚点的城市仍输出数值；反向自评派生分默认进入分享；生产页会自动请求 Google Fonts，却与隐私说明的“无第三方字体”承诺相反。

这些问题影响主结果含义、敏感信息最小化或生产隐私声明，不能由“构建/现有测试通过”抵消。修复所有 P0、补齐对应回归并重新执行 L4 独立复核之前，不应发布。

本文件是只读审查结果的落盘记录。本轮没有修改前端、算法或数据源文件，没有启动服务，也没有运行 `npm` / `npx`。

## 2. 本轮冻结口径

以下口径作为本报告的唯一判定基线：

1. 主结果统计中国大陆 18–50 岁、全国或所选城市**常住人口**中，满足“可可靠量化硬条件”的人数。
2. 未选择的条件不参与计算；婚史未选择表示不限，包含有配偶、未婚、离婚、丧偶等所有状态。
3. 同性与异性组合都采用双层表达：
   - 第一层只按目标性别和其他可靠人口条件给出统计上限；
   - 第二层才加入性取向/可接受性别、当前单身或关系状态、关系意愿等兼容条件，且只能是低置信度、宽范围的关系情境；
   - 当前产品可先支持二元的男男、女女、男女、女男，但必须同时知道用户本人性别和寻找性别。
4. 用户可以把婚史、疾病、收入、房产、生育意愿等表达为硬条件；证据不足时不得编造比例。应保留用户意图，标为“未计入”，主数字明确称为“满足已计算条件的人数上限”，不得称为满足全部条件。
5. 严格结果不得暗中放宽；邻近情境只能由用户主动查看或应用。
6. 输出范围应传播数据、外推和相关性不确定性，称为“合理估计范围”，不得冒充统计置信区间。
7. 必须区分：逻辑不可能 `0`、数据不足“无法可靠估计”、数学期望 `<1`、一般可估计结果。
8. 城市结果使用常住人口；没有可靠锚点的城市不得输出伪精确人数。
9. 本轮前端只审核不修改；前端问题单独列出并交由 Kimi 后续处理。

## 3. 算法与数据：P0 阻断

### AD-P0-01：同性双层以及异性关系情境没有实现

**冲突**

第一层“目标性别人口”已隔离，但第二层没有足够输入判断双方是否兼容，也没有关系情境人数/范围。当前所谓“双向命中”只是偏好 ID 集合重合度。

**证据**

- `app/src/model/schema.ts:93-114` 的 `target` 只有寻找对象的 `gender`，没有用户本人性别。
- `app/src/model/schema.ts:172-178` 只有无值的 `softPreferenceIds` / `selfPreferenceIds` 数组，没有任一方的取向、可接受性别、当前关系状态或关系意愿值。
- `app/src/model/schema.ts:63-68` 把 `relationship.currently_single`、`relationship.orientation_compatible`、`relationship.children_plan` 等都压成同一种布尔 ID。
- `app/src/model/dimensions.ts:264-271,286-305` 将这些项固定为 `population=false` 的普通软偏好。这保证它们不污染第一层，却不能形成第二层。
- `app/src/engine/modelEngine.ts:590-605` 只对两个 ID 集合做 `overlap / union` 和 `overlap / max(size)`，整个函数不读取本人性别或目标性别。
- `app/src/data/evidence-registry.json:1001-1024`，特别是 `:1017`，声称该条目“用于双方边界/偏好兼容逻辑”；当前实现无法兑现这项登记表语义。
- `app/tests/model/model-engine.test.ts:148-178` 只覆盖软偏好不改变人口和一般集合重合，没有男男/女女/男女/女男、不兼容、未披露矩阵。

**静态复现**

```text
target.gender = 'male'
softPreferenceIds = ['relationship.orientation_compatible']
selfPreferenceIds = ['relationship.orientation_compatible']
```

按 `modelEngine.ts:598-604`，`overlap=1`、`union=1`，所以 `softMatch=100`、`bidirectionalIllustration=100`。男性找男性、女性找男性以及现实中不兼容的两个人都无法由 schema 区分，结果相同。

**本轮算法/数据修复责任**

- 增加自愿填写、可跳过的本人性别、寻找性别、双方可接受性别/取向边界、关系状态/意愿输入；“未披露”必须是一等状态。
- 第一层继续严格排除取向比例，仅输出目标性别人口统计上限。
- 第二层输出单独的 `relationshipScenario`，包括适用性、缺失信息、宽范围、低可信度和假设；异性组合也走同一结构。
- 不能把“双方都勾了取向契合”当成已经兼容。
- 新增 4 个性别组合 × 兼容/不兼容/信息不足/未披露的矩阵测试。

**Kimi 后续责任**

- 提供自愿、可跳过且不强迫披露的输入 UI。
- 把第一层统计上限和第二层低置信关系情境分屏/分卡呈现，不把第二层叫爱情概率。

### AD-P0-02：不可可靠量化的硬条件仍直接砍人数，主结果也没有“已计算/未计入”语义

**冲突**

当前系统只有固定的维度分类，没有“用户要求为硬条件，但模型无法可靠量化”的状态。若字段被列为相关硬条件，模型就直接使用假设比例；若被列为软偏好，用户又无法表达它是自己的严格硬条件。最终仍称“满足硬条件”，而不是“满足已计算条件的人数上限”。

**证据**

- `app/src/engine/modelEngine.ts:85-118` 的 `ModelResult` 没有 `countedConditions`、`uncountedHardConditions`、上限标志或不可估状态。
- `app/src/model/schema.ts:27-83,172-178` 没有每项条件的用户强度/硬度；慢病、生育意愿等只能落入固定软偏好 ID。
- `app/src/data/model.ts:52-60` 明确说明没有覆盖 18–50 岁目标人口的个人税前年收入分位，只用 C 级中心与离散度。
- `app/src/data/model.ts:70-80` 的家庭资产尾部使用假设 `sigma` 和人工年龄因子。
- `app/src/data/model.ts:109-113` 把个人本地有房率和个人有车率固定为 `0.45` / `0.35`。
- `app/src/data/evidence-registry.json:559-579` 明确写明青年个人本地有房“缺少全国统一、年龄×性别×城市的相同口径直接统计”，`0.30/0.45/0.60` 只是模型敏感性范围。
- `app/src/data/evidence-registry.json:611-631` 明确写明个人有车“无直接统计”，`0.24/0.35/0.48` 只是模型范围。
- `app/src/engine/modelEngine.ts:289-320` 将收入/资产假设计算为尾部概率。
- `app/src/engine/modelEngine.ts:322-352` 又使用未登记为目标人口直接证据的房屋位置、面积、类型和车价比例，例如核心区 `0.15`、大平层 `0.02`、四合院 `0.0002`、50–100 万车价 `0.06`。
- `app/src/engine/modelEngine.ts:355-365,447-456` 把上述值直接乘进主人口。
- `app/src/components/ResultSummary.tsx:48`、`app/src/pages/Home.tsx:289` 和 `app/src/share/text.ts:9` 都称“满足硬条件”，没有“只满足已计算条件/上限”的限定。
- `docs/DATA_SOURCES.md:308-316` 自己列出收入、个人房车和资产尾部缺口，并要求缺口不要编精确数。

**静态复现**

选择“要求有房、核心区、四合院”时，代码会计算 `0.45 × 0.15 × 0.0002`（再与其他经济条件联合），即使登记表承认目标人口直接比例不存在。结果会显著下降，并被页面描述成满足全部硬条件的人数。

**本轮算法/数据修复责任**

- 在维度注册表建立明确的 `requestedKind` 与 `calculationStatus`：`counted`、`uncounted_insufficient_evidence`、`soft_only`、`not_applicable`。
- 定义可进入主结果的证据/适用性门槛；不是简单地把所有 C 级都一刀切，而是逐项验证分母、年份、年龄、性别、地区、定义和参数可校准性。
- 当前缺少目标人口锚点的个人房/车及其位置、面积、类型、价位细分，在补齐可靠证据前不得缩小主人数。
- 保留用户硬条件意图，返回未计入清单、原因和证据缺口。
- 主结果结构增加 `isUpperBoundForRequestedConditions=true` 或等价语义，并只对可靠可计算项求值。

**Kimi 后续责任**

- 输入端允许用户表达“这是硬条件”，即使模型暂时不能量化。
- 结果、移动摘要、详情、分享图和文字统一显示“满足已计算条件的人数上限”，并显著列出未计入硬条件，不能藏在方法页。

### AD-P0-03：无可靠人口锚点的城市仍输出人数

**冲突**

除 6 个城市外，大多数城市只有没有年份和来源 ID 的旧约数，但引擎对所有城市一视同仁地缩放全国年龄/性别结构并输出人数。

**证据**

- `app/src/data/cities.ts:31-78` 中只有北京、上海、深圳、广州、武汉、苏州带 `populationYear: 2025` 和 `sourceEvidenceId`；杭州、成都、南京、西安等仍只有裸 `pop`。
- `app/src/data/population.ts:153-160` 的 `cityPopulationScale` 对任何已选城市直接累加 `city.pop`，完全不检查 `populationYear` 或 `sourceEvidenceId`。
- `app/src/engine/modelEngine.ts:194-203` 将该缩放值直接乘到全国单岁人口上。
- `app/src/features/steps/PopulationStep.tsx:29-33` 把全部城市放入热门或搜索结果，没有不可估提示。
- `app/src/model/dimensions.ts:101-106` 为所有城市共用一个 C 级地区维度，不能表达“该城市无锚点”。
- `docs/DATA_SOURCES.md:83-101,314-316` 规定每城应有年份、官方 URL 和常住人口口径，并承认其余城市尚未补录。

**静态复现**

选择杭州后，`cityPopulationScale(['杭州'])` 固定返回 `1252 / 140489`；随后 `basePopulation` 仍给出一个数值。杭州条目没有 `populationYear` 和 `sourceEvidenceId`，所以这违反“无可靠锚点不输出城市数”的冻结口径。多城市中只要混入一个无锚点城市也存在同样问题。

**本轮算法/数据修复责任**

- 城市计算入口必须校验每个城市的常住人口年份、口径和有效证据 ID。
- 无锚点城市返回 `insufficient_data`，不得回退旧约数继续给精确人数；可以同时保留全国第一层上限供参考。
- 多城市应对每个成员逐一校验，并在结果中列出缺失城市。
- 增加杭州/成都等无锚点城市以及“有锚点 + 无锚点”混选测试。

**Kimi 后续责任**

- 搜索和选择结果显示城市锚点可用性；无锚点时显示“无法可靠估计”，不能只显示 C 徽章。

### AD-P1-01：范围只是组级固定放大，不是数据、外推与相关参数的实际传播

- `app/src/engine/modelEngine.ts:476-482` 只按组塞入固定的 `12%/20%/8%/16%/18%/40%/30%`。
- `app/src/engine/modelEngine.ts:645-655` 对这些百分比做对数平方和，再以一个乘数包住基准值。
- `app/src/data/evidence-registry.json:504-527,559-582,611-634` 已登记资产离散度、住房率、车辆率的保守/基准/乐观参数；引擎却只用 `model.ts:74-80,112-113` 的单个基准值。

- `docs/MODEL_METHOD.md:102-114` 准确承认当前只是“预设对数不确定度”和“敏感度范围”，不是从证据等级或抽样误差推导。

这已经避免把区间叫置信区间，但还不满足新的“传播数据、外推、相关性不确定性”的冻结要求。应以参数情境重算保守/基准/乐观，记录每个范围驱动及来源，再称“合理估计范围（非置信区间）”。这是本轮算法/数据可修项；Kimi 后续只负责统一标签和展开说明。

### AD-P1-02：逻辑 0、数据不足、期望低于 1 和分辨率不足没有独立状态

- `app/src/engine/modelEngine.ts:85-96` 的人口结果只有数值与 `resolutionExceeded` 布尔值。
- `app/src/engine/modelEngine.ts:658-669` 只能格式化非法数值或 `<1`，没有 `logical_zero` / `insufficient_data`。
- `app/src/engine/modelEngine.ts:678-695` 把所有低于 `max(1, base/1e6)` 的值压成同一个短文案“低于模型分辨率”；一个大于 1 但低于分辨率的值与数学期望 `<1` 会共用状态。
- `app/src/fun/rarity.ts:19,22-30` 对数值 0 一边称“理论上存在”，一边称“概率约等于 0”，无法表达逻辑不可能或未知。
- `app/src/share/text.ts:15-17` 又把幸存数 0 说成“一个没剩”，容易把期望/显示舍入误读成现实 0。

本轮算法/数据应返回带判别字段的状态联合：`estimated`、`expected_below_one`、`below_resolution`、`logical_zero`、`insufficient_data`。Kimi 后续必须按状态渲染，趣味层不得覆盖严肃状态含义。

### AD-P2-01：上限不变量实现存在，但测试门禁不完整

- `app/tests/model/model-engine.test.ts:125-143` 只断言范围排序和有限值。

### FE-P0-01：反向自评派生的“双向命中”默认进入分享

**证据链**

- `app/src/share/policy.ts:21-31` 默认 `showEntertainment: true`。
- `app/src/engine/modelEngine.ts:597-616` 明确从 `selfPreferenceIds` 派生双向分。
- `app/src/share/dto.ts:43-49` 只要填过反向偏好，就在“娱乐”开关下自动加入 `scores.bidirectional`；没有独立公开选择或敏感确认。
- `app/src/components/SharePreviewDialog.tsx:93-97` 的开关只写“娱乐指数”，没有说明会公开反向自评派生分。
- `app/src/components/SharePreviewDialog.tsx:144`、`app/src/share/text.ts:24-25`、`app/src/share/canvas.ts:592-600` 都实际输出该分数。
- `docs/PRIVACY.md:28-30` 则明确承诺反向自评与双向派生分“完全不包含”在图片和文字分享中。

**静态复现**

给任一 `softPreferenceIds` 与非空 `selfPreferenceIds`，使用 `createDefaultShareSettings` 构建 DTO；`reciprocalPreferencesProvided=true` 后，DTO 默认出现 `scores.bidirectional`。

**修复要求**

最安全的修复是从 Share DTO、类型、预览、Canvas、文字中完全删除双向派生分，符合现有隐私说明。若产品确实要分享，必须先改变隐私规格，并设计独立、明确、默认关闭的同意流程；不得借用“娱乐指数”开关。

### FE-P0-02：生产页自动请求 Google Fonts，与隐私说明相反

- `app/index.html:12-16` 对 `fonts.googleapis.com` / `fonts.gstatic.com` 做预连接并加载字体 CSS。
- `app/src/index.css:3137` 实际把 `Baloo 2` / `ZCOOL KuaiLe` 作为展示字体。
- `docs/PRIVACY.md:7` 声称“不接入……第三方字体”；`:36-40` 又声称页面资源随静态包提供、使用系统字体，只有用户点击来源链接才访问外站。
- `docs/audit/TECH_STACK.md:91-95` 和 `docs/audit/BASELINE_AUDIT.md:129-139` 仍把 Google Fonts 记录成应移除的基线风险。
- 原执行提示词 `产品全面升级执行提示词.md:659` 要求自托管或明确说明并控制第三方资源的隐私影响，`:758` 还明确点名 Google Fonts 风险。

首次加载会在用户没有点击任何链接时向 Google 域发送基础访问元数据，当前隐私说明因此不真实。应删除远程字体，使用自托管或系统字体；若保留则必须同步隐私声明、CSP 和故障降级，但这不如删除稳妥。

### FE-P1-01：隐藏地区仍可由城市皮肤反推

- `app/src/share/dto.ts:55-56` 在 `showRegion=false` 时不输出地区文字，但 `:72` 仍无条件把原始城市传给 `pickProf`。
- `app/src/fun/skins.tsx:11-24,58-73` 定义“京剧名角/胡同大爷/龙井茶艺师”等城市专属角色。
- `app/src/fun/skins.tsx:267-279` 以确定性算法约 45% 选择城市皮肤。
- 角色继续进入 `SharePreviewDialog.tsx:135-140`、`share/text.ts:15-19` 和 Canvas。

确定性复现：默认空硬条件、城市北京时 `estimate/base=1`，所以 `survivors=80`、`index=79`；按 `roster.tsx:7-9`，`rnd(79,77)=0.100397...<0.45` 且 `rnd(79,79)` 选择北京皮肤第 2 项，即“胡同大爷”。即使关闭地区，分享仍泄露北京。

隐藏地区时必须强制使用全国通用角色，并对所有城市专属文案做黑名单回归。

### FE-P1-02：未公开敏感硬条件仍通过“神秘条件 + 精确淘汰比例”泄露

- `app/src/share/dto.ts:73-77` 使用完整原始选择构造漏斗帧，只把公开条件 ID 传给文案函数。
- `app/src/fun/rarity.ts:47-59` 遇到未公开的最大影响条件时只把名字换成“某个神秘条件”，仍输出精确淘汰百分比。
- `app/tests/share/share-policy.test.ts:87-106` 反而把这种行为固化为预期。

这会泄露一个未同意公开的敏感条件确实存在，并泄露其影响强度。应只基于公开条件重算总评；如果最高影响项不公开，则整段省略，不能只换名字。

### FE-P1-03：羞辱性和概率误导文案违反产品硬原则

原提示词 `产品全面升级执行提示词.md:86-101,621-624` 明确禁止以收入、身体、疾病、婚史、取向等羞辱人，也禁止把人口比例说成爱情成功率。

当前反例包括：

- `app/src/fun/rarity.ts:34-45`：“投胎确实是门技术活”“秃然真实”“知识确实改变命运……的择偶概率”。
- `app/src/fun/FunFunnel.tsx:16-25`：“穷是我的错吗”“输在起跑线的存折”“身材管理大失败”“植发分期中”。
- `app/src/fun/rarity.ts:17-19,30`：“直接锁死”“遇见概率≈彩票头奖”“概率约等于 0”。
- `app/src/share/text.ts:17` 和预览把显示幸存数 0 说成“一个没剩”，会遮蔽“期望/分辨率/未知”的区别。

梗应只针对条件组合、模型或叠加行为，不针对人的经济处境、基因、身体或价值；“概率”应限定为统计比例/模型情境，不能暗示缘分或成功率。

### FE-P2-01：分享隐私测试存在假通过

- `app/tests/share/share-policy.test.ts:54-59` 断言序列化结果不包含旧属性名 `bidirectionalIllustration`，实际 DTO 键是 `bidirectional`。
- 同一测试断言文字不含“ 双向条件命中”，实际输出是“ 双向命中示意”，字符串并不相同。

因此测试能在派生分已经泄露时仍通过。应直接断言 `dto.scores.bidirectional === undefined`，并检查真实完整输出；同时增加隐藏地区角色和隐藏敏感总评的回归。

## 6. 已确认通过的关键项

以下结论仅是本 SHA 的静态通过项，不抵消 P0：

1. **婚史不限正确。** `app/src/model/schema.ts:197-204` 默认 `maritalStatuses=[]`；`app/src/data/population.ts:138-150` 空数组严格返回因子 `1`，因此包含有配偶及全部婚史状态。`PopulationStep.tsx:100-109` 也明确说明不会偷退回未婚。
2. **软偏好和娱乐项没有进入人口。** `app/src/model/dimensions.ts:286-305` 将关系/取向等软项标为 `population=false`；`modelEngine.ts:590-621` 只计算分数。星座/MBTI 也只生成娱乐分。
3. **第一层没有暗乘取向比例。** 目标性别人口来自 `modelEngine.ts:194-203`，不读取取向软项；这符合双层的第一层隔离要求。
4. **当前数值链不超过基础池。** 群组因子被夹在 `[0,1]`，`modelEngine.ts:435-473` 连续相乘，`:645-655` 的乐观值也不超过 `raw.base`。
5. **严格结果不会自动放宽。** `modelEngine.ts:577-587` 只生成建议；`ResultsStep.tsx:53-54` 只有用户点击“应用”才调用 `onRelax`。邻近结果目前没有暗中替代主结果。
6. **范围没有自称统计置信区间。** `modelEngine.ts:715`、`ResultsStep.tsx:31` 和 `docs/MODEL_METHOD.md:102-114` 都明确称当前为敏感度范围、非抽样置信区间；缺陷在于传播方法还不够证据驱动。
7. **会话草稿有敏感字段清洗。** `app/src/model/selectionUtils.ts:110-125` 只保留安全字段，`app/src/hooks/useSessionSelection.ts:7-16,33-40` 在恢复与写入路径都使用清洗结果；反向自评不进入会话草稿。
8. **业务源码未见主动上传筛选的 API。** 静态搜索未发现业务 `fetch` / XHR / WebSocket；自动第三方请求的已知例外就是 `index.html` 的 Google Fonts。
